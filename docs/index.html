Architecture

Three layers. One reload cycle.

Every file save flows through Kern's three-layer engine; Scanner, Evictor, Orchestrator in precise order. No full restarts. No lost state.

kern
The Problem

Losing state on every save is death by a thousand restarts.

When we were building terminal-based conversational functionality for an AI agent, every code change meant killing the process. Session established all gone. You restart, reload, rebuild, and lose the exact runtime state you were debugging.

Standard hot-reloaders are web-framework specific. flask --debug, uvicorn --reload — they restart your entire process. Kern was built for pure Python scripts where state matters.

Quick Start

Point kern at your script. It handles the rest.

1
Start the engine on your main script

Kern scans it with AST analysis, builds the full dependency graph of every local file it imports, and starts watching all of them.

kern run app.py
2
Edit any connected file and save

Change app.py, or any file it imports — utils/helper.py, models/user.py, anything in the graph. Kern detects it and reloads only the affected modules.

3
Define run() in your entry script (recommended)

Every file your entry script imports — utils/, models/, anything in the graph — is completely normal Python. No contract, no special functions. Kern reloads them automatically when they change.

In your entry script, define run(). Kern calls it explicitly after every successful reload. Think of it as if __name__ == "__main__": but for hot-reloading — it tells kern what to execute after each reload cycle.

# utils/greeter.py — plain Python, no run() needed
def greet(name):
    return f"Hello, {name}!"

# app.py — kern calls run() after every reload
from utils.greeter import greet

def run():
    print(greet("World"))

Kern works without run() too. importlib.reload() re-executes module-level code on every reload regardless. But run() gives you three things: the success message prints before your code runs (not inside the import), a crash in run() doesn't fail the import itself, and it follows Python convention of keeping side effects out of module scope.

Layer 1 — Scanner

AST analysis. Zero code executed during scan.

The Scanner layer pairs DependencyTracker and FileWatcher to build a live dependency map of your entire project — starting from your entry script and following every local import, recursively — without ever executing any code.

Static AST Analysis

Uses Python's ast module to map the full import tree — safe even when watched files have syntax errors.

Absolute Path Resolution

All files resolved to absolute paths, ensuring consistency regardless of working directory changes at runtime.

Syntax Error Resilience

Broken files remain in the watch list. Kern keeps running and recovers automatically once the error is fixed.

Daemon Thread Watcher

FileWatcher runs as a daemon thread — exits automatically with the main process. No cleanup required.

Layer 2 — Evictor

Surgical removal from sys.modules.

The ModuleReloader recursively identifies every module that depends on the changed file, then evicts them in the correct order — children before parents.

Recursive Dependent Mapping

Iterative stack traversal (not recursion) resolves all transitive dependents — no stack overflow on deep dependency chains.

Ordered Eviction

Modules sorted by depth before removal. Children cleared before parents — prevents ghost imports where a parent holds a stale child reference.

Layer 3 — Orchestrator

The persistent loop that keeps kern alive.

The Engine is the top-level coordinator. It runs a while True monitoring loop, sequences the Scanner and Evictor on every detected change, and survives runtime errors in your script.

Debounce Stabilization

500ms debounce window prevents partial saves from firing premature reloads. Editors that batch writes won't cause double-reloads.

Error Recovery

Runtime errors are caught and logged to engine_error.log. Kern stays alive — waiting for you to fix the error and save again.

CLI Reference

Two commands. That's it.

Command Description
kern run <file> Start the hot-reload engine. Kern maps the full dependency graph of the target script and watches all connected files. Calls run() after each reload if present.
kern info Display Kern version, author, and co-architect information.
Configuration

Sensible defaults. No config file needed.

Kern's behaviour is controlled by constants in the engine source. For most use cases the defaults are ideal.

Value Default Description
DEBOUNCE_SECONDS 0.5s Instance attribute on Engine in kern/core/engine.py. Wait time after the last file change before triggering a reload.
time.sleep(0.3) 0.3s Hardcoded in kern/tracker/watcher.py. How often FileWatcher polls file modification times.
time.sleep(0.1) 0.1s Hardcoded in kern/core/engine.py. Main monitoring loop heartbeat — prevents busy-waiting.
run() is optional but recommended. Kern works without it — importlib.reload() re-executes module-level code on every reload. But with run(): the import completes and prints success before your code runs; a crash inside run() is caught without failing the import; and side effects stay out of module scope (Python convention). — Blocking note: kern runs your code synchronously. If run() blocks on input() or a network call, the engine cannot process new file changes until that call returns.
